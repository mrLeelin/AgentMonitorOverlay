# 任务依赖统一：依赖线真的拦启动，拆任务能依赖已有任务（2026-11-17）

> 状态：已定，待实施。2026-11-17 用户按建议定了下面「用户定的」6 条，还没动手。来源：2026-11-17 梳理 Free 专题主控沟通慢的原因，第 7 条建议。

## 为什么

Free 专题（2026-11-17）：主控的下级和人自己建的「Free UI 移植」同时改 `DarkEvilSlotFreeHandler.cs`，双方都把对方的改动当成「外部改动」，多出一次请求决策和一次复核。两个任务之间没有依赖；就算连了，现在的依赖线也拦不住。第 6 条方案（`plans/topic-task-default-lead.md`）要让新任务排在改同一批文件的任务后面，现在也做不到。

现在有两种「依赖」，看着一样，作用不一样：

| | 画布依赖线 | 拆任务的 `dependsOn` |
|---|---|---|
| 怎么建 | 画布右键「连依赖」、详情「添加前置任务」、`canvas_depend`；主控拆任务时也会画 | 只能在同一次 `task_plan_propose` 里写，不能指向已有任务（`taskplans/service.ts` 的 `checkKeys`） |
| 存在哪 | 专题画布的 `edges`（kind `depends`） | 提案记录和启动队列（kv `taskplans.pending-starts`），任务上没有 |
| 拦什么 | 没绑共同需求的任务：**什么都不拦**（`sharedcontext/service.ts` 的 `assertStartable` 一开头就返回）。绑了的：会话启动和每条消息都拦 | 只拦**自动启动**（`startReady`）。人手动开会话、主控传话都会直接开始，队列里那项随即作废 |
| 前置算完成 | （绑定时）在「完成」列、最新交付被它的直属主控验收且仍有效、同一需求版本 | 在「完成」列、最新交付已验收且仍有效，并且前置和后项是**同一个**直属主控：前置换了主控，后项就永远等下去 |
| 界面和说明 | 线上标「等待前置 / 前置已完成」，提示「它要等…做完才开始」，amo_guide 写「前置完成后才能开始后项」 | 提案结果写「其余等前置任务验收后自动启动」 |

也就是说，画布上的依赖线对大多数任务只是画出来，说明文字却说它拦启动；真正拦的 `dependsOn` 只管同一批新任务、只拦自动启动。两者在提案通过时画一次线，之后各管各的：删了线不放行队列，加了线也不进队列。

顺带查到的两个隐患（代码阅读，还没写测试复现）：
1. 后项启动时记下的前置交付（kv `context-prerequisites:<任务>`）以后不再更新。前置被退回重做、重新验收后，没绑共同需求的后项交付会一直被判「前置交付已失效」，验收被挡住，而且不能靠差异说明豁免（`sharedcontext/service.ts` 的 `issues`、`assertAcceptable`）。
2. 任务离开专题时，如果它在画布上没有卡片，它的依赖线不会被删（`canvas/service.ts` 的 `leaveCanvas` 没卡片就直接返回）。这张画布以后的保存可能都过不了校验（`protocol/canvas.ts` 要求依赖线两端都是专题里的任务）。

## 用户定的（2026-11-17，按建议）

1. 方向 A：依赖线真的拦启动，只留这一种依赖。
2. 人手动开始一个前置没完成的任务：弹确认，确认后可以开始。
3. 主控给前置没完成的任务派工（work / reopen）：拒绝，并说明在等谁。
4. 已经在跑的任务后来被连上依赖：不打断，只影响以后的启动。
5. 前置算完成：有直属主控的，看它自己的直属主控验收了最新交付且仍有效；没主控的，看「完成」列。
6. 拆任务时 `dependsOn` 可以写同专题已有任务的 id，前置可以是同专题任何未归档的任务。

## 做法

1. **只有一种依赖：画布依赖线。** `dependsOn` 照旧写，提案通过时落成依赖线（现在已经会画）；启动队列不再自己存一份，改读依赖线：删线就放行，加线就等待。没有专题的旧提案没有画布，保留队列里那份作兼容。依赖仍只在同一专题内。
2. **前置算完成，只有一个标准：**
   - 有直属主控的前置：最新交付被它自己的直属主控验收，且仍有效。去掉「前置和后项必须同一个直属主控」。
   - 没有主控的前置（人自己管的任务）：在「完成」列。
   - 绑了共同需求的后项，另外要求同一需求版本（现状不变）。
3. **拦什么：**
   - 自动启动（拆任务时排队的）：照旧等，条件按上面统一。
   - 主控用 `task_message` 给前置没完成的任务派工（work / reopen）：拒绝，回执写清在等哪个前置、怎么解（等它验收，或删线）。只读询问照旧能问。
   - 人手动开始（新建会话、发第一条消息）：弹确认「前置「X」还没完成，现在开始可能和它改到同一处。仍要开始吗？」，确认后照常开始。
   - 已经在跑的任务后来被连上依赖：不打断，只影响以后的启动，画布上提示一下。
   - 绑了共同需求的任务：照旧在会话启动和每条消息时检查。
4. **拆任务能依赖已有任务：** `dependsOn` 里可以写同专题已有任务的 id，和新任务的 key 混写。前置可以是专题里任何未归档的任务（包括人自己建的），后项是这次新建的任务。第 6 条「交给主控安排」要用到它。
5. **等待中看得见：** 看板卡和任务页显示「等待前置：X」；前置完成后，排队的任务照旧自动开始。画布线上的「等待前置 / 前置已完成」按新的完成标准算。
6. **说明文字改准：** `canvas_depend`、`task_plan_propose`、amo_guide、主控角色说明和画布提示统一成：前置完成（有主控的要验收）后才开始，人可以确认后提前开始。提案对话框「立刻开跑」的提示（现在写「每个都用第一句话开跑」）改成有前置的会等前置。
7. **顺带修上面两个隐患：** 前置重新验收后，刷新后项记下的前置交付；任务离开专题时，不管有没有卡片都删它的依赖线。

## 没选的方向（B：只改名）

依赖线不拦，改名叫「顺序提示」，说明文字照实写，`dependsOn` 不变。改动最小，但解决不了 Free 那种两个任务同时改一个文件的问题，第 6 条也用不上。

## 影响范围

- protocol：「谁是前置」「前置算不算完成」放一处，Host 和界面共用。
- host：
  - `taskplans/service.ts`：队列读依赖线，`dependsOn` 接受已有任务 id，完成标准统一；
  - `sharedcontext/service.ts`：未绑定任务也走同一套前置检查（只在启动时），前置重新验收后刷新记下的前置交付；
  - `relays/service.ts`：派工前检查前置；
  - `tasks/service.ts`：人手动开始时告诉界面「前置没完成」，确认后放行；
  - `canvas/service.ts`：`leaveCanvas` 总是删依赖线；
  - MCP 说明、`guide`、主控角色说明。
- ui：开始会话的确认框、看板卡和任务页的「等待前置」、画布线标签、提案对话框的提示。
- 数据：不迁移。已有的依赖线从此真的生效。

## 风险

- **已有的依赖线开始拦。** 画布上可能有以前随手连的线。CHANGELOG 写清楚；人手动开始只是多一次确认，不会被卡死；主控派工被拒时，回执写清在等谁、怎么解。
- **主控多一轮来回。** 派工被拒后，主控要等前置完成再派。回执写清在等谁；前置是它自己验收的，验收时就知道可以派了。
- **前置一直没验收，后项一直等。** 看板和任务页显示在等谁，人可以删线，或确认后提前开始。

## 验证

- 单测：依赖线拦自动启动、删线放行；`dependsOn` 指向已有任务；前置换了主控也能放行；没主控的前置看「完成」列；主控派工被拒；人手动开始得到「前置没完成」、确认后能开始；前置重新验收后，后项交付能验收；任务离开专题时删掉它的依赖线。
