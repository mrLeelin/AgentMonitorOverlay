## 为什么要改

AMO 的 Bot 现在是一个配好的聊天角色：答完一段话，后面的事就和它无关。Orca 的 Bot 是一件事从接到交的负责人。下表的「依据」一列分三种：**框架**是 Orca 代码强制的；**约定**写在 Bot 的提示词里，靠模型照做（`src/main/bots/bot-preamble.ts:47–80`）；**示例**只是文档里的用法。

| 能力 | Orca v1.4.274 | 依据 | AMO 现在 |
|---|---|---|---|
| 工作记录 | 事项表：待开始、进行中、等待中、需要你、完成、已取消六态，带完成标准、当前提问、等待原因和版本号（`bot-items-schema.ts:91–104`）。什么时候建事项、一件交付一个事项，由 Bot 按提示词调用 `orca bot item add` | 六态和字段是框架，建不建是约定 | 只有单轮请求记录 `studio_bot_requests`（`packages/host/src/features/bots/service.ts:808`）；Plane 另有一套 `plane_bot_jobs` |
| 谁推进工作 | Bot 用 `orca bot item`、`reply`、`memory` 命令推进，Orca 校验命令参数 | 命令是框架，何时用是约定 | Bot 会话的 AMO 工具只放行 `bot_group_ask`（`packages/host/src/mcp/tools.ts:55`）；Plane 流程由 Studio 写死（`teamtasks/plane-bot-jobs.ts`） |
| worker | 按来源地址记录 Bot 的工作，包括没有答复地址的本地聊天（`bot-work-store.ts:12–19`）。派工有变化时刷新归属索引和界面（`bot-chat-tree-index.ts:242–255`）。worker 的结果作为新消息回到 Bot，Bot 再把结果记到事项上。提示词要求「代码活交给 worker」 | 记录、索引和结果回信是框架；记到事项、交给 worker 是约定 | 普通任务，不带 Bot 的职责和技能（`bots/service.ts:605–624`）；`studio_bot_workers` 只用于侧栏和防重，结果不回 Bot |
| 需要你 | 事项进入「需要你」并记下当前提问，等待外部时记下等待原因 | 状态和字段是框架，怎么问是约定 | Bots 工作台的「待你处理」列出等回答、等批准、等审阅的 Bot 聊天，但不按事项分（`packages/ui/src/bots/view.tsx:40`、`81`）。顶栏按任务取第一条待决定，Focus 和任务栏角标逐条计数（`ui/src/shell/WorkbenchShortcuts.tsx:25–36`、`ui/src/focus/FocusApp.tsx:165`、`ui/src/focus/useTaskbarBadge.ts:46–47`），同一个 Bot 有多件事时几处数字对不上 |
| 答复到发起处 | 在哪里被叫醒（Slack、GitHub、Linear），Orca 就把最终消息发回哪里；「在哪被问就在哪答」 | 发送是框架，答在哪是约定 | Plane 只在验收后写一条评论；Webhook 默认只回状态，回结论要先允许外发，进入终态后不能再改（`packages/relay/src/bot-webhooks.ts:80–86`） |
| 改代码 | worker 在独立 worktree，交付是 PR。默认提示词允许不问就先派调查 worker（`bot-preamble.ts:72`），「先问再修」是用例 | worktree 是框架，先问再修是示例 | 分析完不问人就开 worker；工作树是 detached 的，不提交，改动没有去处（`sessions/fork-worktree.ts:22`） |
| 自动化 | 定时（RRULE）和事件触发，一次性等待（`once`），调度每 60 秒检查一次；Bot 可以在聊天里自己建 | 框架 | 巡视靠值守定时开聊天，在设置里填；没有事件触发 |
| 记忆 | 每个 Bot 的 `MEMORY.md` 写入要排队，比对原文后替换，最多试 3 次；撤销会跳过后来改过的行（`bot-memory-record.ts:24`、`99–114`、`176–185`）；夜间整理 | 框架 | 记忆整理只把最近 12 条请求写进 `memory/自动整理.md`（`bots/service.ts:163`），要人手抄进长期记忆 |
| 主动建议 | Look around 只读巡看，建议保留 3 天，被忽略后 30 天不再提（`bot-look-around-state.ts`） | 框架 | 没有 |
| 谁能找它 | 「Who can ask」名单（`cloud/packages/connector-contract/src/bot-askers.ts`） | 框架 | 只有本机的你，加上知道 Webhook 地址的程序 |
| 主页 | 汇总需要你、等待中、worker、自动化、建议 | 框架 | Bots 工作台已有「待你处理」、聊天记录、值守和请求记录，可以从结论开 worker（`bots/view.tsx:36–88`）；侧栏有最新回复预览和 worker 列表 |

差距不在界面，而在 Bot 不对一件事负责到底：没有持久的事项；状态怎么变、能不能开工，没有人把关；worker 的结果不回 Bot；开工前不问人；改动交完没有去处。

AMO 已经做得不差的部分不重做：
- 每个 Bot 的渠道、型号、强度、权限和技能；
- `SOUL.md` 与 `MEMORY.md` 资料目录；
- 本机群组和 Bot 之间互问；
- `@` 转交与目标聊天；
- Bots 工作台；
- 任务、交付验收、待决定、值守、中转这些底座。

## 原则

2026-11-26 GPT 审稿的总评是：「Bot 可以提出下一步，Host 应掌握授权、状态迁移和交付事实。」本文按这条做：

- **人的凭证只走人能点的入口。** 开工批准和交付验收都是 Studio 界面上的结构化动作，走 REST，AI 的 MCP 凭证够不到。做法和现有的 `reviewByUser` 一样（`packages/host/src/features/orchestration/service.ts:223`）。待决定的回答只是一段文字，直属主控也能通过 MCP 回答（`orchestration/service.ts:262`），所以不能当批准或验收用。
- **每个副作用都是 Host 的一步。** 开工、冻结交付、落分支、回帖、清理各有一个稳定键。先落库再执行；响应不明时去核对结果，不重做。
- **外来内容一律当资料。** 工单、评论、附件、技能和记忆里都可能夹带指令。Bot 每次调用工具，Host 都核对 Bot、聊天、事项和 worker 是否对得上；答复发到哪里由 Host 按来源定，Bot 不能自己填。

## 改完后怎么用

**第 1 阶段：Plane 手动接单**（已并入两步方案）。
1. 你在团队看板的 TALUO-12 上点「交给 Bot」，选小鲸鱼和 AmoStudio。
2. 小鲸鱼只读查明原因，写出计划和完成标准。
3. 「交给 Bot」窗口显示「计划待确认」。如果小鲸鱼开着「需要授权」提醒，Studio 会提醒你。
4. 你看过计划后：
   - 点「开工」：Studio 从分析时记下的提交开出工作树，派 worker。
   - 点「不开工」：写下原因，单子停下。以后可以重新交给 Bot，小鲸鱼会带着这次的原因重新分析。
5. worker 交付后你照现在的方式验收，通过后 Studio 写回原单评论。
6. 工作树保留，由你看改动、提交。

**后面的阶段。**
- **事项。** 任何来源要跟进的活，都成为小鲸鱼的一件事项（如「#3 修复 kv 键清单测试」）。Bots 工作台按需要你、进行中、等待中、最近完成分组显示。
- **交付落分支。** 你验收的是冻结下来的那份改动。通过后 Studio 把它放到 `bot/3` 分支并删掉工作树；分支留着，合不合并由你决定。
- **会话里找它。** 你在会话里说 `@小鲸鱼 把 xxx 的偶发失败查清修掉`，小鲸鱼建事项，后面同上，结论回到你发起的会话。只是问个问题时它直接回答，不建事项。
- **Plane 标签。** 在 Plane 给工单打上 `bot:小鲸鱼`，小鲸鱼自动接单，开工前照样问你。
- **巡视。** 小鲸鱼巡视时发现的问题进「建议」，你点「去做」或「忽略」。
- **外部系统。** Webhook 来的事件也建成事项；允许外发时，把最终结论交给调用方。

## 做法

### 1. 第 1 阶段：Plane 手动接单先问再开工

已并入两步方案的第 1 步，以 [`plans/done/bot-work-loop.md`](../done/bot-work-loop.md) 为准。

### 2. 事项（第 2 阶段）

新增四张表：

- `bot_items`：编号（全局递增，界面显示 `#3`）、所属 Bot、负责的 Bot 聊天、来源和答复去处、发起人、标题、说明、完成标准、状态、当前提问、等待原因和唤醒条件、结束说明、版本号、时间。
- `bot_item_links`：worker 任务、交付、批准、Plane 工单、分支、提交、链接、文件。
- `bot_item_events`：建立、修改、状态变化、评论、关联、答复、回答，并记下是 Bot、你还是 Studio 做的。
- `bot_item_steps`：要做的副作用（开工、冻结交付、落分支、回帖、清理）。每一步有稳定键、目标、正文哈希、状态（待做、已发出、已确认、失败）和回执。

六种状态只是给人看的视图。状态能不能变、谁来变，按下表：

| 状态变化 | 谁能做 |
|---|---|
| 待开始 → 进行中 | Bot（只做只读分析）、你 |
| 进行中 → 需要你 | Bot 提问；Studio（开工申请、待验收、Bot 停下了） |
| 需要你 → 进行中 | 只有你的回答、批准或验收 |
| 进行中 → 等待中 | Bot，必须写明等待原因和唤醒条件（时间或事件），或者留一个「继续」入口 |
| 任意 → 完成 | Bot，前提是事项没有未结束的 worker、没有未验收的交付、没有未做完的步骤 |
| 任意 → 已取消 | 你；Bot 只能提议 |

状态、事件和步骤在同一个事务里写。答复编号在第一次发送前落库，绑定目标和正文哈希。

事项的变化如果不是 Bot 自己的聊天做的，Studio 就写信给负责的 Bot 聊天（复用会话收件箱，`packages/host/src/features/sessions/inbox.ts:109`）。规则如下：
- 只有需要 Bot 接着做的事才叫醒它：你的回答、新交付、退回、外部回复。
- 同一轮里的多件事合成一封信，参照现有的下级交付汇总（`orchestration/service.ts:428–442`）。
- 关闭、清理这类事件只记录，不叫醒 Bot。

界面先扩展现有的 Bots 工作台（`ui/src/bots/view.tsx`），加一个「事项」区：
- 按需要你、进行中、等待中、最近完成分组；
- 「需要你」里的每一项，按待决定、开工申请或交付的编号定位到具体内容；
- 侧栏 Bot 行显示「需要你」的数量，和 Focus 用同一种计法。

要不要改成独立主页，等用上一段时间再定。

Plane 手动接单改为建事项：
- 迁移时保留旧的执行任务、回执和来源索引，失败待重试的旧单也迁过来。
- 接单防重的键改成「Plane 服务器 + 工单」，不再带账号，换个账号也不能重复接同一张单。

### 3. 验收与交付落地（第 3 阶段）

- **验收。** 沿用 `reviewByUser`。现在只有根主控和 Plane Bot 的 worker 能由你验收（`orchestration/service.ts:163–167`），这一阶段扩展到所有 Bot 的 worker。Bot 不做 worker 的直属主控：一旦做了，worker 就失去人工验收资格。「需要你」里的验收项直接打开最新交付。
- **冻结交付。** worker 交付时，Host 用底层 Git 命令，把工作树当时的内容冻结成一个提交：
  1. 在临时索引（`GIT_INDEX_FILE`）里 `add -A`，遵守 `.gitignore`；
  2. `write-tree`；
  3. `commit-tree -p <基准提交>`。

  这个提交挂在 `refs/amo/delivery/<交付编号>` 下，防止被 Git 回收，并记到交付上。你在 Git Review 里看到的，就是这个提交相对基准的改动。之后 worker 再改工作树，也不影响这份交付。
- **落分支。** 你验收通过后，Host 用 `update-ref refs/heads/bot/<事项编号> <冻结提交> <原值>` 落分支；原值对不上就停下问你。
  - 分支已存在时，只有它指向这个事项记录过的提交才复用。
  - 提交者身份用仓库配置的 `user.name` 和 `user.email`，没配就问你。
  - 仓库要求签名（`commit.gpgSign`）时不自动落分支，提示你手动提交。
  - 底层命令不会跑仓库钩子，这样 Host 不会以桌面用户的权限自动执行仓库里的脚本。
- **清理。** 先确认分支指向冻结提交、worker 会话已经结束，再 `git worktree remove`（不加 `--force`），并删掉 `refs/amo/delivery/` 下的引用。删不掉就留着，并说明原因。
- **退回修改。** worker 在同一个工作树里继续改，新的交付冻结成新的提交。

### 4. Bot 工具与 worker（第 4 阶段）

Bot 会话新增一组 AMO 工具，为此要放宽 `mcp/tools.ts:55–98` 的过滤。MCP 服务在命令沙箱之外运行（见 `runtime/codex/codex-runtime.ts:968` 的注释），只读沙箱管不住工具带来的副作用，所以每个工具都由 Host 核对。

| 工具 | 作用 | Host 核对 |
|---|---|---|
| `bot_item_list`、`bot_item_get` | 看自己的事项 | 只能看自己的 |
| `bot_item_create` | 建事项 | 来源取当前请求，Bot 不能自己填 |
| `bot_item_update` | 改标题、完成标准、状态 | 按上面的状态变化表 |
| `bot_item_ask` | 问你业务问题，附 2–4 个建议回复 | 回答送回 Bot，不当批准或验收用 |
| `bot_item_reply` | 回到来源答复 | 发到哪里由 Host 按来源定；外部答复先给你看 |
| `bot_request_worker` | 申请开工 | 只建开工申请，你批准后由 Host 派 worker |
| `bot_worker_send` | 给自己的 worker 发后续要求 | worker 必须属于这个事项 |
| `bot_memory_propose` | 提一条记忆 | 第 6 阶段做，先进待确认 |

- **worker 继承什么。** Bot 的职责、批准的计划和完成标准。
  - 技能只带你在 Bot 设置里允许给 worker 的。技能是经 `botSkillPrompt` 单独传的（`bots/service.ts:235–242`），不在 `botInstructions` 里（`bots/data.ts:62`）。
  - 记忆默认不带。
  - 任务服务创建首个会话时，目前不接受这类说明，要补这个参数。
- **预审。** Host 把冻结交付的改动（有长度上限）和交付摘要交给 Bot，Bot 对照完成标准判断：不合格就用 `bot_worker_send` 退回，合格就请你验收。
  - 不依赖 Bot 能读 worker 的工作树：工作树在项目旁边，各渠道的只读模式不一定读得到。
  - 退回次数按交付版本计，同一事项最多 3 次，再不合格就来问你。
  - 预审可以按 Bot 关掉。
- **Bot 停下了。** Bot 一轮结束后，如果事项还在进行中，同时满足以下四条，Studio 才把它标成「需要你：小鲸鱼停下了」：没有运行中的 worker；没有待回答的提问；没有待做的步骤；也没有等待条件。
- **首版不开放**「开工不用问我」，也不开放外部「直接答复」。

### 5. 回到发起的地方（第 4 阶段）

- **会话：** 送进发起会话的收件箱，沿用 `report()`（`bots/service.ts:836`）。
- **群组：** 发在原群。
- **Plane：** 写原单评论，按答复编号防重。
  - 现有覆盖层只认 `result-UUID` 格式的外部编号（`integrations/plane/amo_team_board.py:669–682`）。答复编号用 UUID 套这个格式，不改覆盖层。
  - 覆盖层不支持时，用 Plane 标准评论接口。响应不明时，先查原单上有没有这条评论，再决定要不要重发。
- **Webhook：** 中转保存结果，供调用方查询；进入终态后不能再改（`relay/src/bot-webhooks.ts:80–86`）。所以只交一次最终结论。

### 6. 入口（第 5 阶段）

**Plane 标签 `bot:<Bot 名>`。** 看板快照（已含标签和状态分组，`amo_team_board.py:513–528`）只用来发现候选单：
- Host 每 60 秒增量拉一次，失败了就退避。
- 按标签 ID（不按名字）在工单活动里找到这次加标签的记录，再用账号 ID 核对加标签的人在不在「谁能派活」名单里。
- 覆盖层的活动分页没有账号 ID（`amo_team_board.py:466–469`），详情里的 `event()` 有（`142–144`）。分页要补上账号 ID，这需要团队部署。
- 加标签的人不明、同一张单有多个 Bot 标签、或者项目切换了，都转给你决定。

**跨设备防重。** 多台电脑或多个账号都开着时，要靠服务端原子认领。覆盖层已有一个按工单加行锁的认领动作，就是团队任务的「接单」（`amo_team_board.py:757–781`）。是复用它，还是另做一条 Bot 认领记录，到这一阶段再定。手动接单和标签接单用同一套认领规则。

| 其他入口 | 做法 |
|---|---|
| 会话 `@Bot` | 沿用 `bot_ask`；要跟进的活由 Bot 建事项 |
| 群组 | 同上，答复发在原群 |
| Webhook | 收到事件后建事项，只回最终结论 |

以后接 GitHub、Linear 等，只是多一种入口和答复方式。

### 7. 记忆闭环（第 6 阶段）

- `bot_memory_propose` 提的条目先进待确认，并记下来源（事项或聊天）和改动内容。你确认后才写入 `MEMORY.md`。
- 每个 Bot 只有一个写入入口，按顺序写：先比对原文再替换，有冲突最多重试 3 次（参照 Orca `bot-memory-record.ts:24`、`99–114`）。
- 每次改动都记历史。撤销只还原后来没被改过的行（参照同一文件 `176–185`）。
- 别人消息、网页、文件或工具输出里的指令，不能存成记忆（Orca 提示词里有同样的规则）。
- 记忆整理升级成「重写草稿、比对后写入、可撤销」，排在这一阶段之后。

### 8. 建议与等待（第 7 阶段）

巡视发现的事建成待开始的事项，放进「建议」。你可以去做，也可以忽略；忽略后 30 天内不再提。等待中的事项按时间或事件唤醒，一次性的等待借用值守来做。

## 分阶段

每一阶段单独确认、单独验收。每步改完都跑类型检查和相关测试，给出代码对比和功能对比，按文件可以回退。不重启用户正在用的 Studio。

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 先问再开工 | 已并入两步方案第 1 步 | 见两步方案 |
| 2 事项核心 | 四张表、状态变化规则、来信合并、工作台事项区、Plane 接单迁移和新防重键 | 单测：谁能改哪种状态、同一事务写入、重启恢复、旧单迁移、换账号不重复接单；工作台截图 |

## 不照搬 Orca 的地方

- **开工必须你批准。** Orca 的默认提示词允许不问就派调查 worker；AMO 的 Bot 分析本身就是只读调查，改代码前一律问你。
- **用工具固定下来。** 建事项、记结果、答复发到哪里，在 Orca 是提示词约定；AMO 用工具加 Host 核对固定下来。
- **连接器不走 Orca Cloud。** 用 AMO 中转和局域网直连（Plane 在局域网里，Host 直接拉）。
- **不给每个 Bot 单独建 SQLite。** 事项放进 Studio 现有的数据库，和任务、待决定在同一个事务里改。
- **交付先落在本机分支。** 不默认推送，也不默认开 PR。
- **不追 Orca 支持的众多 agent。** 沿用 AMO 已接入的渠道。

## 风险与约束

- **改动面（第 2–7 阶段）。** `teamtasks`（Plane 接单）、`sessions/fork-worktree.ts`（分支）、`orchestration`（人工验收范围、交付冻结）、`collab`（待决定关联事项）、`mcp/tools.ts`（Bot 工具）、`tasks`（首个会话的说明）、`sessions/inbox.ts`（事项来信）、`packages/ui/src/bots`、`packages/ui/src/teamtasks`。相关测试：`teamtasks/plane-bot-jobs.test.ts`、`e2e/studio/team-board-plane.spec.ts`、`bots/bots.test.ts`、`e2e/studio/bots.spec.ts`、`focus.spec.ts`、`feature-deps.test.ts`、`amo-mcp.test.ts`、`duty.test.ts`。
- **依赖模型守规矩。** Bot 推进依赖模型按工具办事。授权、状态变化和交付事实由 Host 把关，「停下了」兜底。
- **模型轮次。** 预审和来信叫醒会多用模型轮次。控制办法：只在需要 Bot 做事时叫醒，多件事合并，预审可以关掉。
- **不跑钩子。** 靠钩子做检查的仓库，这些检查要放进 worker 的验证里，或者在合并时做。
- **Unity 工程。** 工作树对 Unity 工程不实用：没有 Library，打开要整个重新导入。Unity 项目在哪里执行另外再谈。

## 重新开工时要定的事

第 1 阶段的几条（范围、放弃后重新交给 Bot、提醒、验收后不自动提交）已在两步方案里定了。其余写下默认，重新开工时再确认：

1. 交付落分支用底层 Git 命令，不跑仓库钩子；仓库要求签名时转人工（第 3 阶段）。
2. worker 继承 Bot 的职责和计划；技能只带你允许的；记忆默认不带（第 4 阶段）。
3. 首版不开放「开工不用问我」，也不开放外部「直接答复」（第 4 阶段）。
4. 预审默认开，退回次数按交付版本计，最多 3 次（第 4 阶段）。
5. 普通 `@` 问答不建事项，要跟进的活由 Bot 建；Plane 和 Webhook 来的一律建（第 2、5 阶段）。
6. 谁能派活，默认只认你；身份不明时转给你（第 5 阶段）。
7. 界面名称用「事项」，和「任务」「工单」区分开。
